# S2: Hooks under permission-skipping

Run 2026-10-14 on Claude Code 2.1.299, `claude -p` on Haiku (`claude-haiku-5-5`) with a Pro login. Harness: `scripts/spikes/s2/run-all.sh`. A fake `eas` (`bin/eas`) only logs calls, and the guard is a plugin `PreToolUse` hook on `Bash` with `timeout: 5` and `onFailure: "block"` that exits 2 on `eas submit`. Re-run the harness after every Claude Code upgrade.

## Findings that change M1
1. **Every executor run must carry an orchestrator-owned `--settings <file>`** containing at least `{"disableAllHooks": false, "enabledPlugins": {"<guard>@inline": true}}` plus the compiled deny/ask rules. The agent can write project, local, and user settings (bypass mode, same OS user), but it can't change the next run's CLI flags. A file the agent can't write is safest: keep it outside the agent's home, owned by your user and readable by the agent.
2. **Also pass `--setting-sources user`** (or none) so project and local `.claude/` files written by a previous task are ignored. The agent can still write *user* settings, so (1) remains the guarantee.
3. **Adapter init check.** It must assert that the guard plugin is in `system/init.plugins` and that `plugin_errors` is empty. T3f shows unloading is **silent**. The plan already has this check (§4), and this result confirms it's load-bearing.
4. **Diff check.** It must flag any change under `.claude/` in the worktree (already a protected path in `policy/src/compile.ts`). It should also hash `~rnship-agent/.claude/settings.json` before each run.
5. **Hooks are early feedback, not the gate.** D1 is unchanged: T3 and T3f show a confused or hostile agent can switch hooks off unless (1) is in place.

## Not tested
- Real `eas`: the fake binary stood in for it.
- `--bare`: it skips plugins by design. The adapter's init check covers it.
- A hook timeout on events other than PreToolUse.
- Managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json`). They would lock settings machine-wide, but they'd also apply to your own sessions.
