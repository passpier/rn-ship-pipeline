# S0: Does identity separation hold?

Run 2026-10-15 on the Mac with `scripts/spikes/s0-identity.sh`, then re-run once two probe bugs were fixed (see below). **Every check passed.** Raw results are in `docs/spikes/S0.results.env` (gitignored, no secrets). Repos: `passpier/rnship-s6-probe` (throwaway, private) and `passpier/Spirit-Ripple` (private, empty).

## Design under test

The plan assumed a GitHub machine-user account. You declined a second account. That account wouldn't have worked anyway, for two reasons:
- **There's no Read role.** On a personal-account repo, collaborators can't have read-only access, and every collaborator can merge PRs ([GitHub docs](https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository)).
- **There's no server-side guard.** On Free private repos, branch protection and rulesets return 403 (S6), and merging needs only Contents: write.

So any GitHub credential the agent held could merge, and could push to `main`.

The revised design:
- **`rnship-agent` holds no GitHub credential.**
- **A broker (`scripts/spikes/s0-broker.sh`) runs as you.** It holds the key of a GitHub App, `rnship-agent` (id 5329755). The App is installed on the two repos only, with contents, issues and pull_requests write, metadata read, and no workflows permission.
- **The broker does exactly two things for the agent:**
  - push a git bundle to `agent/*`;
  - open a PR from `agent/*` into `main`.
- **Every action mints its own token,** downscoped to one repo and expiring within 1 hour.

## Probe bugs found on the first run, all fixed

**B1/B5: the broker's PR token was too narrow.**
- The broker minted PR tokens with only `pull_requests: write`. GitHub answered 422 "not all refs are readable", because it must read the head branch.
- The fix adds `contents: read`.
- Checked by hand with that exact permission set: the token opened PR #2 on the probe repo as `rnship-agent[bot]`, and still got **403 on merge and 403 on moving `main`**.
- The broker now logs GitHub's error body to its own 0700 log.

**E2: `eas update` never reached its credential check.**
- The probe folder had no `package.json`, so eas-cli stopped at "Run this command inside a project directory".
- With a `package.json` it reaches "An Expo user account is required to proceed". Reproduced with an empty `HOME` and a fake project ID.
- The probe now writes a `package.json`.

**Wizard: re-runs stopped without a message.** The G1 and G4 commits had fixed content. On a re-run they had nothing to commit, so `set -e` exited silently. Their content is now unique per run, and an `ERR` trap prints the line where any step stops.

**Confirmed:** the stage 4 re-run turned B1, B5, N4 and E2 green.

## Consequences for the plan

- **D1 holds without a machine account.** The agent holds no GitHub credential. GitHub enforces two of the five threats itself:
  - #2: no `workflows` permission, so G5 is rejected;
  - #3: an installation limited to two repos, plus per-action downscoping (G6, G7).
- **#1 (merge or push `main`) rests on broker code alone.** An unrestricted App token can do both (G3, G4), and Free private repos have no server-side rule against it. You accepted this risk and won't upgrade to Pro (2026-10-15). Free backstops:
  - a release-job actor gate, proven in G9;
  - a read-only default `GITHUB_TOKEN`, proven in C1 and C2;
  - `rnship merge approve` refusing if `origin/main` moved.

  These detect a bad push and stop it shipping, but don't prevent it.
- **#4 on GitHub's side:** App pushes do trigger workflows (G8), so the M1 release workflow **must** start with the actor gate, before any checkout. The agent can't remove the gate, because it can't touch workflows.
- **#5:** the App key lives only in your login keychain, which the agent can't read (I-checks, B6). Tokens expire within 1 hour (G10). B9 confirms the rule: secrets go in env vars and pipes, never on argv.
- **Hardened after S0 (2026-10-17, from sandvault):** `sysadminctl` had left `rnship-agent` in staff (PrimaryGroupID 20), so only your home's 700 mode kept it out of staff-readable files. It now has a group of its own (`s0-identity.sh` stage 1; `m3.sh` offers the move and its preflight checks the session's groups).
- **Still open:** which macOS user runs the broker for real, your own or a third user `rnship-broker`. For S0 it ran as you.
